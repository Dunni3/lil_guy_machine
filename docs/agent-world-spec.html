Agent World: a 3D sim driven by pluggable decision models

A small 3D world rendered on the Google TV Streamer, with one character whose every action is chosen by an LLM (or other decision model) behind a backend‑agnostic, typed interface.

01Goals & principles

Goals

  • A tractable 3D world with one agent‑controlled character.
  • All character behavior comes from a decision model.
  • Any OpenAI‑compatible endpoint can be plugged in by config.
  • Typed decisions: the model returns a value of a Kotlin type, not loose text.
  • Grows to many agents and richer worlds without redesign.

Principles

  • Library, not engine. We own the loop, world model and entities.
  • Sim is headless. No graphics imports in the world logic.
  • Types are the contract. One sealed class defines the action space, its JSON schema and its parser.
  • Never block a frame on a model. Decisions are async intents.
  • Desktop first, TV second. Same code, faster iteration.

03System overview

The TV runs the world and draws it. Decisions come from a model endpoint over HTTP: a hosted provider during development, a local inference server later. Swapping between them is a config change.

The TV is a display and an HTTP client. Model inference never runs on the TV.

04Modules & dependencies

Dependencies point one way. The two core modules are plain Kotlin/JVM, so they can be tested and run from the command line with no device.

Arrow = "depends on". :sim and :decision know nothing about each other or about graphics; :agent joins them.

05Simulation core :sim

A deterministic world advanced by a fixed‑timestep tick (20 Hz). The renderer interpolates between snapshots, so draw rate and sim rate are independent.

World model (MVP)

  • Space: a bounded tile grid (e.g. 32×32) with a height per tile. Continuous positions, grid collision. Easy to describe in text, easy to path‑find (A*).
  • Entities: plain Kotlin classes with an id, transform and components as fields. No ECS framework; add one only when entity count demands it.
  • Objects: walls, doors, a few pickup items (key, apple), a container.
  • Character: position, facing, inventory, simple needs (optional), current intent.

The boundary

interface World {
    val tick: Long
    fun step()                                   // advance one fixed tick
    fun observe(agentId: EntityId): Observation  // what this character can perceive
    fun submit(agentId: EntityId, intent: Intent): IntentHandle
    fun snapshot(): WorldSnapshot                // immutable, for rendering/replay
}

@Serializable
sealed interface Intent {
    @Serializable data class MoveTo(val target: Target) : Intent
    @Serializable data class PickUp(val itemId: String) : Intent
    @Serializable data class Use(val itemId: String, val on: String?) : Intent
    @Serializable data class Say(val text: String) : Intent
    @Serializable data class Wait(val ticks: Int) : Intent
}

Intents vs. primitives

Models choose intents ("go to the door"). A per‑character controller in the sim turns the intent into per‑tick motion, reports progress, and finishes with a result (Succeeded, Failed(reason), Interrupted). Results go into the next observation so the model learns what happened.

Observation

A structured object with two renderings: JSON (for typed prompts and logs) and compact text (for prompts). It includes the character's state, nearby entities with relative direction and distance, a small local map, the last intent result, and recent events. Agents never see the whole world state.

06Decision layer :decision

A backend‑agnostic way to ask "given this context, return a value of type A". The Kotlin type is the single source of truth: it generates the JSON schema sent to the model and parses the reply back.

Wrapper decorators (logging, caching, rate limiting, retry‑with‑validation) also implement DecisionModel and stack around any backend.

Core interface

interface DecisionModel {
    val id: String
    val capabilities: Capabilities   // jsonSchema, toolCalls, logprobs, maxContext
    suspend fun <A> decide(request: DecisionRequest, schema: ActionSchema<A>): Decision<A>
}

data class DecisionRequest(
    val system: String,
    val messages: List<Message>,
    val temperature: Double = 0.7,
    val timeout: Duration = 20.seconds,
)

data class Decision<A>(
    val value: A,
    val rationale: String?,          // optional "thought" field from the schema
    val usage: Usage, val latency: Duration,
    val raw: String,                 // kept for logs and replays
)

Getting typed output from any endpoint

Backend capabilityStrategyGuarantee
Supports json_schema (vLLM, llama.cpp, most hosted)Send schema; server constrains decodingAlways schema‑valid
Supports tool calling onlyExpose each intent variant as a toolValid in practice; validate anyway
Plain text onlyPrompt for JSON → parse → validate → retry with the error (max 2)Best effort; falls back to Wait
Raw logit handling is not needed for typed output: vLLM and llama.cpp both do schema/grammar‑constrained decoding server‑side. Logits matter only for the later choice‑scoring backend.

07Timing & the agent loop :agent

Rendering runs at 60 fps, the sim at 20 Hz, and decisions take 0.5–10 s. The agent loop runs in its own coroutine and only touches the sim through observe and submit.

Prefetch: request the next decision before the current intent ends to hide latency. A stale decision (world changed meaningfully) is re‑validated by the sim and may fail cleanly.

Agent loop

class AgentRuntime(val world: World, val id: EntityId, val model: DecisionModel) {
    suspend fun run() = coroutineScope {
        while (isActive) {
            world.awaitDecisionPoint(id)            // intent done, near done, or interrupted
            val obs = world.observe(id)
            val req = prompts.build(obs, memory.recent())
            val decision = runCatching { model.decide(req, IntentSchema) }
                .getOrElse { fallback(it) }           // e.g. Wait(20)
            memory.record(obs, decision)
            world.submit(id, decision.value)
            log.write(world.tick, obs, decision)      // JSONL, replayable
        }
    }
}

Thread safety: the sim owns its state on one thread. observe reads an immutable snapshot; submit enqueues into a channel drained at the start of the next tick.

08Rendering & TV app :app

Look

  • Low‑poly, flat‑shaded meshes built in code (boxes, cylinders) via ModelBuilder.
  • One directional light + ambient. No shadows in MVP.
  • Third‑person follow camera, plus an overhead debug camera.
  • Target 1080p at 60 fps on the Streamer's GPU.

HUD / overlay

  • Current intent and status.
  • Last model rationale (short).
  • Latency, tokens, endpoint name.
  • Speech bubbles for Say.

Remote input

  • D‑pad: orbit camera / switch camera.
  • OK: pause / resume agent.
  • Back: toggle debug overlay.
  • No direct character control: the agent is the only driver.

Android packaging: a leanback launcher activity so it appears on the TV home row; network permission; config read from app storage or pushed over ADB (adb push endpoints.yaml).

09MVP scope

MVP definition: on the TV, a character in a small room finds a key, unlocks a door, and exits. Every step is chosen by a hosted model through the typed interface, and swapping the endpoint in config to a local server works without code changes.

In

  • One 16×16 room scene with walls, a door, a key, a couple of distractor objects
  • One character; intents: MoveTo, PickUp, Use, Say, Wait
  • Grid collision + A* path‑finding controller
  • OpenAiCompatBackend with json_schema and retry fallback
  • Scripted backend for tests
  • Async agent loop with fallback on timeout/error
  • HUD with intent, rationale, latency
  • JSONL decision log
  • Desktop + Android TV targets; headless CLI runner

Out (for now)

  • Multiple agents and agent‑to‑agent messaging
  • Physics engine
  • Procedural or large worlds
  • Long‑term memory / retrieval
  • Choice‑scoring via logprobs
  • Asset pipeline (glTF models, textures)
  • Phone/web control plane integration
  • Audio

11Risks & open questions

RiskMitigation
Model latency makes the character look frozenPrefetch decisions; idle animation; multi‑step plans as an optional schema later.
Provider structured‑output quirks (schema subset limits)Keep schemas flat; test each backend in :cli; tool‑calling and retry fallbacks.
Kotlin schema generation edge cases with sealed classesSmall custom generator for our action types if library output isn't accepted by providers.
TV GPU / memory limitsLow‑poly, few draw calls, profile at milestone 2.
API keys on a TV deviceDev only; later route through your own backend/proxy so keys never live on the device.
Nondeterminism makes bugs hard to reproduceDeterministic sim + JSONL decision log = exact replays without calling the model.

Open questions

  • Which hosted provider for development, and does its OpenAI‑compatible endpoint support json_schema with our schema shapes?
  • Should agent calls go directly from the TV, or through the backend you're planning for the TV control plane (which also hides keys and allows logging)?
  • Does this live in the existing TV monorepo or its own repo?
  • What does the character "want"? A goal string in the prompt is fine for MVP; needs or rewards come later.
  • Local inference hardware and target model size, which sets the latency budget.

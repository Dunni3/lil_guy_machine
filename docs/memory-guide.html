How the guy remembers

A guide to the memory system as it stands on main: what gets recorded, what a language model writes from it, and what reaches each decision prompt. Every number here is a default you can find in the code; file paths are relative to the repo root.

1The picture in one diagram

Three things happen as he lives: everything he is shown and does is logged (the event stream), a text model writes that log up in batches (memories), and at every decision a fixed rule picks a few memories and journal entries to put in the prompt. Beside that sit two things he writes himself: journal entries and thoughts.

2Five kinds of remembering

"Memory" in this codebase means several different things. They differ in who writes them, how long they live, and how they reach the prompt.

KindWhat it holdsWritten byIn the promptCode
Short-termThe last 8 intents, how each ended, and the thought for a thinkAgent loop, as it goesAlways, as "Your recent actions"agent/.../Memory.kt

The short-term memory and the latest thought live only in the agent loop's fields. The other three live in a MemoryStore, which is the "long-term memory" that AgentMemory wraps.

3One decision, step by step

This is the order of calls in AgentRuntime.run(), which loops once per decision point.

  1. Observe. Wait for the decision point, take the observation, and settle short-term memory (fill in how the last intent ended).
  2. longTerm.observed(obs) appends an Observation event, then settles any pending journal session: if the journal activity succeeded, the entry is stored; if not, it's discarded.
  3. Recall. recall(obs) picks memories and recallJournal(obs) picks journal entries (rules below).
  4. Build the prompt from the observation, recalled memories, recalled journal, latest thought and recent actions.
  5. Decide. Call the decision model, unless 4 decisions have passed without a think, in which case the intent is think and the model isn't asked.
  6. longTerm.acted(obs, intent, brief) appends an Action event, starts a journal session if he chose do(journal), lets the art studio react, and starts a summary if 20 or more events are waiting.
  7. Think, if the intent is think: one more model call, inline. The thought becomes a Thought event and the new latest thought.
  8. Record the intent (and thought) in short-term memory, log the decision record, and submit the intent to the sim.

4Level 0: the event stream

The only thing recorded as it happens. Each event is a row with run, tick, game day and time, a kind and free text. Ids only grow, which is what lets the summarizer track where it stopped.

KindWhenText looks like
observationEvery decision pointlast action do activity=sketch: succeeded; money $42; energy 61, fullness 48, mood 55; owns bed, desk, journal; event: ...
actionEvery decisiondo activity=journal, buy item=canvas, think
thoughtAfter a successful thinkThe thought, in his words
journalWhen an entry is storedwrote in my journal and wrote down 2 wants (never the entry itself)
artWhen a drawn piece is keptmade sketch piece 3, "Window at Dusk" plus tags

Describe.observation deliberately leaves out the option lists (activities, shop), which are the same every time, and includes only the sim's recentEvents that weren't in the previous observation, so the stream isn't padded with repeats.

The journal entry's text is kept out of the stream on purpose. If it went in, the summarizer would paraphrase his entries back to him as memories, and the journal would echo through two channels.

5Level 1: memories

The Summarizer turns batches of events into memories. It's the only thing that writes to the memories table.

When it runs

After each action, if 20 or more events aren't yet covered (batchSize = 20). It works through full batches (catchUp), and at the end of a run flush() also summarizes the short remainder.

Where it starts

coveredThrough(run, 1) is the highest event id any memory covers. The next batch starts after it, so every event is summarized exactly once. A failed or timed-out call (60 s) stores nothing, and the same batch is retried next time.

Background or inline

With a coroutine scope (the app) it runs in the background and never holds up a decision. Without one (CLI lockstep runs, tests) it runs inline, which keeps those runs deterministic.

What the model is given

A fixed system prompt (write one first-person memory, two to four sentences, only what the log shows) and the batch as a log, at temperature 0.3:

Log:
[d1 08:00] I saw: money $20; energy 80, fullness 60, mood 50; owns bed, desk, journal
[d1 08:00] I did: do activity=sketch
[d1 09:30] I saw: last action do activity=sketch: succeeded; money $26; ...
[d1 09:30] I did: think
[d1 09:30] I thought: I should buy food before I write tonight...

Write the memory.

It replies {"memory": "..."}. The stored memory keeps the event-id range it covers (from_id..to_id) and the game-time span, shown as e.g. Day 1 08:00-14:30.

The summarizer must be a model that writes text. A closed-choice model (TypeSafe's Jev, which only picks from options) is rejected in the constructor. The same goes for the journal writer and the thinker.

6Recall: what reaches the prompt

Recall is plain code in Recall.kt, not a model. It runs at every decision, with separate numbers for memories and the journal so neither can crowd the other out.

Always includedPlus relatedCharacter budget
MemoriesThe latest 3Up to 3 older ones sharing words with the situation1200
JournalThe latest 2Up to 3 older ones sharing words with the situation (entry text and want text)800

How "related" is decided

The context is the observation's text plus the ids of the unlocked activities, the shop items and usable items, with underscores turned into spaces. Keywords takes the words of four letters or more, drops common ones (including money, energy, mood, which are in every observation), and scores each older memory by how many words it shares with the context. Highest score wins; on ties, newer wins; a score of 0 is never picked. There are no embeddings yet.

How the budget is applied

Candidates are taken in this order: latest first (newest to oldest), then the related ones. Each is added if it fits the remaining budget; the very first always fits, so the newest memory is always shown. The chosen ones are then sorted oldest first for the prompt. In practice, only the newest is guaranteed if memories are long.

The ids of what was recalled are kept in AgentMemory.lastRecalled and lastRecalledJournal (the dev view highlights them), and the text is in each DecisionRecord.recalled / recalledJournal in the decision log.

7The journal

The journal is a bedroom activity (do(journal), an hour at the desk) plus a second LLM call that writes the entry. The sim doesn't know a model writes anything; AgentMemory connects the two.

Lifecycle of an entry

  1. He chooses do(journal). If the activity is locked (too tired, too hungry), nothing happens.
  2. startJournal launches a JournalWriter session with his persona and his situation (the decision prompt's user message, minus the closing ask). In the app it runs in the background.
  3. The writer loops: each reply is one schema-constrained step, either search(source, query) or write(entry, wants). A search returns up to 5 keyword hits from memories, events or journal as the next user message. After 3 searches the search option is removed from the schema, which forces a write.
  4. At the next decision point, settleJournal checks whether the activity succeeded. If it did, the entry is stored and a journal event is appended. If it failed or was interrupted, the entry is discarded. If the model is still writing when the activity ends successfully, it's stored when it finishes.

Wants

The entry (under 150 words, temperature 0.8) comes with a list of wants: {kind, text, justification}, where kind is one of activity, item, place, sense, other. A want with a blank justification fails validation, so the backend retries instead of storing it. The persona tells him the maker reads every entry and may grant argued wants. Nothing grants them automatically yet; tiers are unlocked by hand with --grant.

Session statuses

Written (waiting for the activity), Stored, Discarded (activity didn't succeed), Failed (the model gave no entry). Every session, kept or not, goes to the decision log as a "kind": "journal" line.

8Thinking

think is an intent with no fields. The sim spends 10 game minutes and 2 extra energy (think in bedroom.yaml). The memory side is one call to the Thinker:

  • It sends the decision prompt's own system prompt and situation, plus instructions to stop and think, and asks "What do you want to do next, and what do you want to achieve?". The reply is {"thought"}, under 80 words.
  • It runs inline, after the decision and before the intent is submitted, so he stands still meanwhile, as he does while deciding.
  • The thought goes to three places: a thought event (the summarizer reads it as "I thought"), the short-term entry for that think, and latestThought, which appears in every prompt until the next thought, under "your plan for now".
  • Forced thinking: think.every: 4 in bedroom.yaml makes him think after 4 decisions without one, without asking the decision model. Remove the key to leave it to the model.
  • He can't think twice in a row: think is dropped from the schema and the choice set right after one.
  • Without a journal writer, think isn't offered at all.

9What the model actually sees

The system prompt is fixed for the run. All memory goes into the user message, in this order (PromptBuilder.build). Sections that are empty are left out. Illustrative example:

Observation:
{"tick": 2400, "clock": {"day": 2, "time": "14:00"}, "money": 31, "needs": {...}, ...}
What you remember from earlier, oldest first:
- Day 1 08:00-11:40: I sketched twice and sold both, then bought bread...
- Day 2 06:00-09:20: I woke rested and wrote in my journal before work...
What you wrote in your journal, oldest first:
- Day 1 21:00: Today felt small but steady... Wants: an easel (because painting would ...)
What you decided the last time you stopped to think (your plan for now):
- d2 13:30: Eat first, then sketch until I have enough for the easel.
Your recent actions, oldest first:
d2 12:10: {"type":"do","activity":"sketch"} -> succeeded
d2 13:30: {"type":"think"} -> succeeded; you thought: "Eat first, then ..."
Choose your next action.

Picking models (Jev) get the same content as fields of the choice set's state: state.memories, state.journal and state.latest_thought, with an instruction for each. The journal writer and the thinker are given this same situation text, so they see what the decision model saw.

10Storage and runs

Storage sits behind the MemoryStore interface in :agent, so :agent stays free of any database.

InMemoryStore

Lists in memory. Used by the app (desktop and TV), by tests, and by the CLI when there's no --memory file but a journal writer is configured. Gone when the run ends.

SqliteMemoryStore

One SQLite file, in :memory-sqlite (xerial JDBC, JVM only). Used by the CLI with --memory runs/mem.db. Tables: events, memories (with a level column), journal (wants as JSON). Search narrows with LIKE and ranks with Keywords, so both stores return the same results.

Everything is scoped to a run (one life). In the app the run id is run-N and each restart makes a new InMemoryStore. In the CLI it's <timestamp>-N; one SQLite file can hold many runs, but recall and search only read the current one. A fresh world never remembers another world's past.

The TV keeps long-term memory only in RAM: the JDBC driver isn't packaged for its 32-bit ARM userspace. Android's built-in SQLite behind the same interface is the likely fix.

11Who writes what (config)

Three LLM roles are separate from the decision model, all set on the first agent in config/endpoints.yaml:

RoleConfigOverrideWhen unset
Summarizer (memories)memory_endpoint--memory-endpoint, MEMORY_ENDPOINT=No memories are written; events are still logged
Journal writer, thinker, artistjournal_endpoint--journal-endpoint, JOURNAL_ENDPOINT=Falls back to memory_endpoint; none turns it off

With no journal writer, the prompt doesn't mention the journal or think, a picking model isn't offered them, and the 24-hour "no journal" mood slide is off. The sim still accepts do(journal), so the scripted policy can test the economy. Every call is metered by TokenLedger under its own purpose (decision, summary, journal, think, art).

12Where to look at it

Dev view

MEMORY page: short-term memory, long-term memories with the recalled ones marked, and the last two thoughts. JOURNAL page: entries with wants (UP/DOWN to page). HISTORY: per decision, what was recalled and the thought.

Memory viewer

tools/memory-viewer.html opens a CLI .db in the browser (sql.js) and shows memories beside the events, highlighting the events each one covers.

Run logs

Decision log JSONL in runs/ (recalled text per decision, plus journal lines). CLI bedroom runs also write journal-NN.txt, tokens-NN.jsonl and a summary.json.

make cli ARGS="--scenario bedroom --days 3 --endpoint typesafe --memory runs/mem.db --memory-endpoint NAME"

13What it doesn't do yet

  • No level 2. The schema has a level column for summaries of summaries, but nothing writes them. Over a long run, only the latest 3 memories plus keyword matches surface; the middle of his life fades unless it shares words with the present.
  • No embeddings. Recall and search are keyword overlap. Synonyms don't match.
  • No continuity across runs or restarts. That waits for saves.
  • No persistent store on the TV or in the app. Both use InMemoryStore.
  • Wants aren't answered. Someone has to read them and grant or decline.
  • Personality (milestone 6) isn't part of memory yet; the persona is fixed text in Persona.kt.
